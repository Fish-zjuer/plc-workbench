# 当前 Agent 到底怎样工作

本轮称为 R6（通用 PLC 任务），与其他位置开发的 R5 区分。在本地 Git 分支 agent-general-tasks 上开发。R4 课程题库流程保留，R5 的 CODESYS 适配可以通过后端接口合并。

它的工作单位是“一份 PLC 需求和对应程序”，输出是完整 ST、扫描检查、反例、修订记录及交付 ZIP。上传附件、聊天、计划模式和压缩上下文是交互基础；编程闭环由程序调度，不靠模型自己宣布完成。

## 一次任务的全过程

~~~mermaid
flowchart TD
    U[用户上传题面或现有 ST] --> P[规划者：读需求，列接口、假设和测试]
    P --> C[任务面板：查看完整约定]
    C --> A[用户确认这一版需求和测试]
    A --> B{执行后端支持原接口吗}
    B -->|不支持| X[说明缺失能力及适配选择，保留原接口]
    B -->|支持| W[作者模型生成完整 ST]
    W --> G[程序检查接口并保存版本]
    G --> E[真实编译并逐扫描执行]
    E -->|失败| F[返回同版本反例]
    F --> W
    E -->|固定检查通过| R[隔离上下文的独立审查]
    R --> D[新进程重放两次]
    D -->|违反冻结不变量| K[加入持久回归场景]
    K --> W
    D -->|预期有争议| H[核对需求，记录有依据的裁决]
    H --> E
    D -->|未发现未解决问题| Z[导出程序、约定、证据和 SHA256]
~~~

以“互锁恢复后不能自行重启”为例：用户要求按启动按钮后保持运行；停止或互锁断开立即停机；互锁恢复时，即便按钮还按着，也不能自动重新启动。规划时要明确按钮是“电平”还是“上升沿”，同时事件谁优先。

测试不是只输入一次 start=TRUE。它会输入一串扫描：启动→保持→互锁断开→互锁恢复而按钮仍按着→释放→重新按下，并检查每一步 running。代码若把状态记忆处理错了，会返回哪一扫描失败、预期与实际输出，作者据此修订。

## 各种职责分别是谁

| 职责 | 实际承担者 | 能修改什么 |
|---|---|---|
| 规划者 | 通用聊天模型及任务工具 | 提出新任务约定；不能替用户批准 |
| 作者 | 配置的模型，独立紧凑请求 | 提出完整 ST，保留接口 |
| 执行与判定 | Python 调度器、编译器、原生扫描程序、固定规则 | 保存代码版本、执行和记录结果 |
| 对抗审查者 | 新上下文的模型请求 | 提出新轨迹和预期；不能修改规则或批准自己 |
| 需求裁决 | 用户操作；实验中明确测试约定由开发者核对 | 确认约定、说明理由驳回误报；版本变化后旧裁决失效 |

作者和审查者可使用同一个弱模型；隔离的是上下文，不能据此声称用了两个独立模型或消除了共同偏差。服务仍通过 base_url、api_key、model 配置；review_model 可另填审查模型 ID。

## 新任务约定保存什么

contract.json 包括：

- target：希望交付的平台，目前可选 offline、portable、codesys。
- executor：实际执行适配器，默认 offline。target=codesys 不会自动变出 CODESYS 编译记录。
- block、inputs、outputs、inouts：功能块名称和完整接口。
- requirements：有编号的自然语言需求。
- scenarios：按扫描顺序提供全部输入、时间和应检查输出；场景引用对应需求。
- properties：“如果条件成立，则输出应满足……”规则，可读取上一次扫描，不执行任意 Python 表达式。
- assumptions、questions：假设和待回答问题。有未解决问题时不能确认约定。
- tolerance：浮点比较绝对误差，默认 1e-6，不能任意放大。

例如：

~~~json
{
  "id": "P_STOP",
  "requirement": "R2",
  "when": {"inputs.stop": true},
  "then": {"outputs.running": false}
}
~~~

这是有限轨迹上的约定检查，**不是形式化证明**。当前没有接入 SMT、模型检查器或完整 PLC 硬件模型。

约定和原始需求快照保存在项目 tasks 目录，在模型可写 workspace 之外。确认后作者只能改实现；不能为了通过而改掉预期。若需改需求，应创建新任务约定并重新确认，历史结果保留。

## 为什么独立审查不能直接当裁判

审查模型可能发现真缺陷，也可能误读题意：

1. 它给出的输入在两个新进程中执行，保存实际输出。
2. 若违反已确认不变量，作为有依据的反例，保存到持久回归集并自动修复。
3. 若只是与审查模型新增预期不同，标为 review_disagreement，留给用户核对。不会自动升级为测试真值。
4. 误报可用 /task reject 任务ID F1 "理由" 驳回；疑问用 Q1。重新 run 仍会重新编译、跑基线及两次重放，同版本下无需再请求审查模型。
5. 新预期确实应成为需求时，创建更强的新约定，再用原候选修复，不暗改旧测试。

实际例子：延时任务常规检查通过，独立审查补充 delay=0，发现首次有效扫描输出 FALSE；原需求要求恰好到达 delay 时为 TRUE。开发者核对本地 TON 源码后，增加零延时固定场景和不变量，再让 DeepSeek 修复。修复后审查又问负数 TIME；输入域只接受非负 TIME，这个疑问被有依据地驳回，随后零模型请求完成重新编译和重放。原失败记录保留。

## 结果分层

| 状态 | 可以说明什么 |
|---|---|
| planned | 只制定计划，没有生成和执行 |
| requires_contract_confirmation | 需要核对接口、假设和测试 |
| capability_blocked | 执行器缺少能力，附下一步选择 |
| coverage_gap | 声明的不变量没有被输入触发 |
| review_disagreement / review_questions | 审查仍有待裁决问题 |
| reviewed_offline_pass | 当前候选通过本地有限检查及审查流程 |
| offline_pass_target_pending | 本地通过，目标平台尚未验证 |
| stale_evidence | 源码、需求、回归集或后端与旧记录不一致 |

有限检查通过只说明当前约定和轨迹下没有失败。选择 portable，也没有自动得到 CODESYS、Siemens 或实体 PLC 兼容性。

通用桥接目前支持 BOOL、常见 8/16/32 位整数和位串、REAL/LREAL、TIME/LTIME（LTIME 需 R4 后端）。一般数组、STRING、STRUCT、VAR_IN_OUT、VARIANT 暂无通用桥接；它们在 R4 题库专用流程中的已有能力仍保留。两条流程的支持范围不同。

## 上下文压缩怎样配合

通用聊天使用分段模型摘要和按预算保留的近期原文，原始消息可检索；不是固定丢掉两轮以前所有记录。

专用任务每次给作者发送“固定约定＋当前完整代码＋最新失败证据＋本轮修订摘要”。审查只收到需求、接口、假设、采样和输入域、当前代码，看不到作者聊天或基线测试。精确 SHA、需求确认、回归集和裁决由程序保留，不交给摘要模型猜测。

## 在 TUI 中使用

上传需求文件，在计划模式输入：

> 请读取附件，为它建立通用 PLC 任务。说明接口、未确定问题、扫描测试和假设，保存任务计划。

点击底部“任务”，滚动查看完整约定，核对后勾选并点击“确认约定”。这一步不执行代码。切换执行模式，再点击“运行任务”，或告诉助手执行该任务。

命令入口也保留：

~~~text
/task plan 合约JSON路径
/task show 任务ID
/task accept 任务ID
/act
/task run 任务ID
/task status 任务ID
/task export 任务ID
/task reject 任务ID Q1 "超出约定输入域，具体依据……"
~~~

examples/tasks/ 内有三个可导入示例。公共题库仍用 /solve 05。压缩用 /compact，原话检索用 /history 关键词。
